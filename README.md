# LLMO sign action

Re-sign your `llmo.json` on every push, using the official [`llmo`](https://www.npmjs.com/package/llmo) CLI with your private key stored as a repo secret.

This is a [composite GitHub Action](https://docs.github.com/en/actions/creating-actions/creating-a-composite-action). It installs the `llmo` npm package on the runner, writes your private key to a tempfile, runs `llmo sign --in-place`, and (by default) commits the refreshed signed document back to the branch with `[skip ci]` in the commit message to prevent recursion.

## What it does

Your `llmo.json` is a signed document. When you edit it (add a contact, update hours, rotate a disavowal), the signature is invalidated. This action re-signs it on push so the live deployed artifact stays valid without manual intervention.

If your branch has no changes to `llmo.json` (or the re-sign produces no diff), the action exits without committing.

## Quickstart

### 1. Generate a keypair (one-time, locally)

```bash
npm install -g llmo
llmo keygen --kid mykey-2026-01 --jwks-path static/.well-known/llmo-keys.json
```

This writes:

- `mykey-2026-01.pem` (your private key, mode 0600) — keep this offline.
- `static/.well-known/llmo-keys.json` (public JWKS) — commit this to your repo.

### 2. Store the private key as a repo secret

In your repo settings → Secrets and variables → Actions, add a new repository secret named `LLMO_PRIVATE_KEY`. Paste the **full contents** of the `.pem` file, including the `-----BEGIN PRIVATE KEY-----` and `-----END PRIVATE KEY-----` lines.

### 3. Add the workflow

Create `.github/workflows/llmo.yml`:

```yaml
name: Re-sign llmo.json

on:
  push:
    branches: [main]
    paths:
      - 'static/.well-known/llmo.json'

permissions:
  contents: write

jobs:
  sign:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: openllmo/llmo-action@v0.1
        with:
          doc-path: static/.well-known/llmo.json
          key: ${{ secrets.LLMO_PRIVATE_KEY }}
          kid: mykey-2026-01
```

That's it. Push a change to `llmo.json`, the action re-signs and commits the refreshed signature back to `main`.

## Inputs

| Input | Required | Default | Description |
| --- | --- | --- | --- |
| `doc-path` | no | `static/.well-known/llmo.json` | Path to the llmo.json file. Hugo publishers typically use `static/.well-known/llmo.json`; Next.js publishers typically use `public/.well-known/llmo.json`. |
| `key` | **yes** | — | PKCS#8 PEM private key. Load from a repo secret (`${{ secrets.LLMO_PRIVATE_KEY }}`). Generated by `llmo keygen`. |
| `kid` | **yes** | — | Key ID. MUST match the kid of the corresponding public JWK in your `/.well-known/llmo-keys.json`. |
| `alg` | no | `ES256` | JWS signing algorithm. One of `ES256`, `ES384`, `EdDSA`. Must match the alg of the JWK identified by `kid`. |
| `cli-version` | no | `latest` | Pin a specific `llmo` CLI version (e.g. `0.1.14`). Pinning is recommended for reproducible builds. |
| `commit` | no | `true` | Commit the re-signed document back to the branch. Set to `false` for dry-run mode. |
| `commit-message` | no | `chore(llmo): re-sign llmo.json [skip ci]` | Commit message. The default includes `[skip ci]` to prevent the commit from re-triggering this same workflow. |

## Outputs

| Output | Description |
| --- | --- |
| `changed` | `"true"` if the re-sign produced a diff and was committed (or would have been, in dry-run mode); `"false"` if the re-sign produced no diff. |
| `doc-path` | The resolved `doc-path` that was signed. |

## Recommended workflow trigger

Filter the workflow to only run when `llmo.json` changes:

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'static/.well-known/llmo.json'
```

This prevents the action from re-signing on every unrelated push. Combined with the default `[skip ci]` commit message, your workflow only runs when you actually edit `llmo.json`.

## Recursion protection

ECDSA signatures use a fresh nonce on every sign, so signing the same content twice produces two different signatures. Without protection, the action's commit would re-trigger the workflow and produce an infinite re-sign loop.

The default `commit-message` includes `[skip ci]`, which is honored by GitHub Actions: pushes whose commit message contains `[skip ci]` do not trigger any workflows. If you customize the commit message, keep the `[skip ci]` token.

## Dry-run / drift-check mode

Set `commit: false` to sign locally on the runner but never commit. The action still produces the `changed` output, so a downstream step can detect drift and surface it:

```yaml
- uses: openllmo/llmo-action@v0.1
  id: llmo
  with:
    doc-path: static/.well-known/llmo.json
    key: ${{ secrets.LLMO_PRIVATE_KEY }}
    kid: mykey-2026-01
    commit: 'false'

- name: Fail PR if llmo.json signature is stale
  if: steps.llmo.outputs.changed == 'true'
  run: |
    echo "::error::llmo.json signature is stale. Run `llmo sign` locally and commit before merging."
    exit 1
```

## Branch protection

The action uses the default `GITHUB_TOKEN` (provided by Actions automatically) to push the commit back. If your branch is protected and the `github-actions[bot]` user is not in the bypass list, the push will fail.

Three ways to resolve:

1. **Allow `github-actions[bot]` to bypass branch protection** (repo settings → branch protection rules → allow specified actors to bypass required pull requests).
2. **Use a PAT** with `contents: write` from a service account, exposed as `secrets.LLMO_BOT_TOKEN`, and pass it to `actions/checkout` (`token: ${{ secrets.LLMO_BOT_TOKEN }}`). The subsequent `git push` will use the PAT's credentials.
3. **Run in PR mode**: have the action open a PR with the re-signed document rather than committing directly. This is not yet built in; file a feature request.

## Security

- The action writes the PEM key to a tempfile (`mktemp` + `chmod 600`) inside the runner, then `trap`s removal on exit. The key is never echoed to logs.
- `printf '%s'` is used instead of `echo` to avoid shell interpretation of escape sequences.
- The action pins `actions/setup-node@v4` and uses npm's standard install — no curl-to-bash, no custom installers.
- The bundled `/llmo` publisher skill that ships with the `llmo` CLI is suppressed on CI runners via `LLMO_SKILL_DIR=$RUNNER_TEMP/...` (the skill is a publisher-side tool, irrelevant on a one-shot CI runner).
